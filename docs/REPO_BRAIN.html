Tech Stack — Full Breakdown
Backend (apps/backend): Express 4 application server bound to port 5001 on 0.0.0.0. Database layer uses pg 8.16 with pgvector extension for semantic search (vector(1536) columns with ivfflat/HNSW cosine indexes). Dual connection pools: write pool via DATABASE_URL, read pool via DATABASE_READ_URL with automatic fallback to primary. Redis stack: ioredis 5 for caching, session cache, pub/sub, and rate limiting; @socket.io/redis-adapter for multi-node WebSocket broadcasting. Job queue: BullMQ 5 with 6 named queues (analytics, leaderboard, notifications, recommendations, dead-letter, events) — all with configurable retry/backoff, repeatable jobs, and graceful degradation when Redis is unavailable. Real-time: Socket.IO 4 with JWT authentication, room-based subscriptions (user, test, notification, admin), rate limiting, heartbeat monitoring, and eviction testing. Security: Helmet 7 with full CSP in production, Multer for file uploads, Razorpay for payments, @sentry/node 8 for error tracking, AWS SDK (S3 storage, SES email, SNS SMS), SendGrid mail, bcrypt 6 for password hashing, Google OAuth via google-auth-library, express-validator for input validation, xlsx for Excel import/export. Entry point: app-port5001.js (1,162 lines) — composition root that orchestrates the full startup sequence.
Frontend (apps/frontend): React 18 SPA served on port 3000 via Vite dev server / static build. Styling: Tailwind CSS with utility-first classes. Routing: React Router 6 with React.lazy() code-splitting per route and RouteErrorBoundary for fault isolation. Data fetching: TanStack Query for server-state management with stale-time caching, optimistic updates, and background refetching. Charts: Chart.js for analytics dashboards. Real-time: Socket.IO client for live test monitoring and notifications. SEO: react-helmet-async for dynamic meta tags. UX: react-hot-toast for notifications, react-easy-crop for image cropping, custom Calculator component for exam mode. Testing: Vitest with 9 test files covering smoke tests, auth persistence, API client refresh, telemetry, and shared hooks.

Architecture & Runtime Flows

The important behavior is a set of connected request, persistence, and event paths. These traces are aligned with the graph workflow map and current route mounts. Each flow below traces the full request lifecycle from client to database and back, including middleware, service calls, and side effects.

Test attempt lifecycle

The most complex flow in the system. TestInstructions page displays test metadata, rules, and timer. -> POST /api/tests/:id/start creates an attempt record (dedup: one in-progress per user/test, migration 094), initializes section scores, starts server-side timer. -> server timer/state tracks elapsed time, validates against time limits, prevents replay. -> TestInterface renders question palette, passage groups, calculator (exam mode), and auto-saves every 30s. -> autosave / pause persists progress via PUT /autosave, supports pause/resume with state preservation. -> submit triggers scoring, anti-cheat event batch submission, solution generation. -> outbox + eventBus publishes analytics, leaderboard recalculation, notification fan-out, and recommendation generation via BullMQ queues. -> analytics / leaderboard / notifications update topic stats, wrong-question bank, revision queue, and user achievements. -> result shows score, section analysis, solution review, and reattempt options. Sources: api/routes/tests.js, api/routes/attempts.js, services/core/TestAttemptController.js, services/core/TestStateMachine.js.

Practice Lab

Fundamentals-first practice engine. POST /api/practice/sessions creates session with topic selection and difficulty parameters. -> id + sessionId returned to client for session tracking. -> GET question fetches next question with metadata (topic, difficulty, type). -> check / skip submits answer, receives immediate feedback with explanation. -> complete finalizes session, generates analytics. Answers and analytics feed mastery levels, AI-generated explanations, solution approaches, similar-question lookup via pgvector embeddings, and the Node Engine learning graph (topics as nodes, per-user skill vectors, spaced-repetition scheduling). Practice AI cache stores LLM-generated content for reuse. Sources: api/routes/practice.js, pages/tests/PracticeLab.jsx (1147 lines).

Auth and session boundary

Multi-layer authentication system. login / phone OTP validates credentials, checks lockout status (progressive: 3→5min, 5→15min, 10→1h, 20→24h), generates JWT with embedded sessionId. -> CSRF + httpOnly cookie sets access token in httpOnly cookie, CSRF token in separate cookie, session record in user_sessions table. -> JWT middleware verifies token signature, checks Redis-cached session, validates isActive and emailVerified. -> protect() attaches user to req.user, embeds sessionId for downstream audit. Optional 2FA: /api/auth/login/2fa requires TOTP code after initial login. Expired access tokens go through refresh endpoint with one retry in the client. Logout clears cookies, invalidates session in DB, and records the session event. Sources: modules/auth/auth.routes.js, middleware/auth.middleware.js, modules/auth/twoFactor.service.js.

Admin content pipeline

Multi-guard admin operations. manager / bulk import starts from admin panel manager (e.g., TestsManager, QuestionsManager) or bulk import modal. -> Zod/schema validation validates input with typed schemas (admin panels use Zod, backend uses express-validator). -> admin route passes through layered guard stack: normalizeFields (camelCase→snake_case) → restrictAdminOrigin (origin allowlist) → validateAdminApiKey (API key header) → protect (JWT auth) → admin (isAdmin check) → CSRF (for mutations) → loadAdminPermissions → requireAdminPermission (RBAC) → auditMiddleware (logs action). -> PostgreSQL executes with transaction isolation. -> sync stats updates denormalized counters. -> event + query invalidation publishes domain event via eventBus, invalidates relevant TanStack Query caches. Sources: api/routes/admin.js + admin-routes-index.js, apps/admin-panel/src/features/admin/.

AI and search

Multi-provider AI gateway. question/content arrives via API request (explanation generation, mentor chat, or search query). -> embedding / pgvector generates vector embedding via OpenRouter provider, stores in pgvector columns with ivfflat cosine index for similarity search. -> RAG context retrieves relevant document chunks via semantic search, assembles context window. -> OpenRouter gateway routes to selected LLM provider (GPT-4, Claude, Gemini, Llama), applies rate limiting (50/hr free, 500/hr pro via Redis sliding window). -> cached response stores in practice_ai_cache for reuse, logs generation metadata (model, tokens, cost) in ai_generation_logs. AI routes are rate-limited; generation logs and practice AI cache keep the user-facing path observable and bounded. Sources: modules/ai/aiClient.js, modules/ai/rag.service.js, modules/ai/embeddingService.js.

Public study routing

SEO-optimized content delivery. slug URL (e.g., /study/mathematics/chapter-1-algebra) arrives at the router. -> study API receives request with slug parameter. -> slug/id resolver looks up content by slug in subjects, chapters, or videos tables (supporting both slug and numeric ID). -> hierarchy/content joins assembles full content hierarchy: subjects → chapters → topics → videos/PDFs/tests. -> SEO page renderer injects structured data, meta tags via react-helmet-async, and serves content with proper caching headers. Subjects, chapters, videos, PDFs, tests, and study-material counts are assembled at the API boundary with response caching (60s TTL for public endpoints). Sources: api/routes/study.js, pages/study/StudyMaterial.jsx, pages/study/StudyMaterialChapter.jsx (1435 lines).

Canonical backend route groups

The composition root mounts tests, questions, study, exams, series, categories, bookmarks, notifications, payments, attempts, practice, sessions, subscriptions, community, analytics, imports, embeddings, Node Engine, AI, adaptive testing, live tests, search, builders, sections, and study materials under /api. The admin routes use a separate mounting system via mountAdminRoutes(app, adminLimiter) which mounts 30 extracted admin-* routers under /api/admin/*.

Admin routes: + adminIpAllowlist → normalizeFields → restrictAdminOrigin → validateAdminApiKey → protect → admin → CSRF → loadAdminPermissions → requireAdminPermission → auditMiddleware. 3. Backend (apps/backend)

Express 4 API server — port 5001. 83 route files in api/routes + 32 module route files. JWT auth + optional TOTP 2FA, PostgreSQL, Redis, Socket.IO, Sentry. The backend follows a composition-root pattern: app-port5001.js wires all middleware, routes, and infrastructure together. Individual route files and modules are self-contained but depend on the composition root for initialization order.

Entry Point — src/app-port5001.js (1,162 lines)
Startup sequence (in order):
1. dotenv — loads .env into process.env
2. validate env — checks DATABASE_URL, JWT_SECRET, JWT_REFRESH_SECRET, FRONTEND_URL exist
3. JWT strength check — ≥32 chars, mixed case + digits + symbol (rejects weak secrets)
4. Compromised secret blocklist — SHA-256 hash comparison against leaked-in-git-history secrets (runtime guard against accidental secret reuse)
5. Optional Sentry init — if SENTRY_DSN is set, initializes error tracking with source maps
6. compression — gzip/brotli response compression
7. strong ETag — weak ETags for efficient caching
8. trust-proxy 1 — for rate limiting and IP detection behind nginx
9. helmet — full CSP in production, relaxed in development
10. json/urlencoded — 1MB body limit
11. cookies — cookie-parser with secret
12. morgan — HTTP request logging to pino
13. monitoring — in-memory + Redis metrics, slow-request warning >1s
14. publicIdResponse — rewrites res.json to expose public_id as id
15. trace — x-request-id, traceId, startTime headers
16. CORS — allowlist-based origin validation
17. validateOrigin — additional origin checking for sensitive routes
18. generalLimiter — global rate limiting
19. requestDedup — collapses identical concurrent GET requests
20. responseCache — in-memory TTL cache for public endpoints
21. cacheControl — no-store for user data, max-age=300 for public
22. static mounts — /uploads, /assets/avatar (with auth guard), /storage (with image optimization)
23. adminIpAllowlist — optional IP restriction for /api/admin
24. route mounts — 70 canonical /api mount entries
25. /api/sessions router — inline session management routes
26. mountExtractedRoutes(app) — dynamically mounts remaining extracted routes
27. Swagger — API documentation at /api-docs
28. Sentry error handler — catches errors before generic handler
29. notFoundHandler — 404 for unmatched routes
30. errorHandler — centralized error response with sanitized messages
31. testConnection(5 retries) — verifies DB connectivity with exponential backoff
32. runMigrations — auto-runs 115 migration files in sequence
33. warmPools — initializes read/write connection pools
34. initRedis — establishes Redis connection with status monitoring
35. initQueues — creates 6 BullMQ queues (analytics, leaderboard, notifications, recommendations, dead-letter, events)
36. messageBroker.init + registerUserEventSubscribers — Redis pub/sub + domain event handlers
37. createServer + initWebSocket — HTTP server + Socket.IO with Redis adapter
38. server timeout 30s / headersTimeout 31s — prevents hanging requests
39. listen on 0.0.0.0:5001
40. BullMQ repeatable reminder job — every 6 hours for scheduled notifications
41. startScheduler + startOutboxPoller + startAttemptCleaner — background jobs begin processing

Graceful shutdown: SIGTERM handler closes scheduler/outbox/cleaner, drains email queue, closes queues/Redis/DB in order. Uncaught exceptions route through fatalShutdown for clean exit.

Middleware Order (full stack)
Inbound: compression → helmet (CSP) → express.json/urlencoded (1MB limit) → cookieParser → morgan (HTTP logging) → monitoring (metrics + slow request warning) → publicIdResponse (rewrites res.json) → trace (x-request-id) → CORS (allowlist) → validateOrigin → generalLimiter → requestDedup (collapses identical GETs) → responseCache (TTL cache) → cacheControl (no-store for user data)
Static: /uploads (multer uploads) → /assets/avatar (auth guard + image optimization) → /storage (with auth guard)
Admin: adminIpAllowlist → route mounts (normalizeFields → restrictAdminOrigin → validateAdminApiKey → protect → admin → CSRF → loadAdminPermissions → requireAdminPermission → auditMiddleware)
Outbound: Swagger → Sentry error handler → notFoundHandler (404) → errorHandler (centralized with sanitized messages)
