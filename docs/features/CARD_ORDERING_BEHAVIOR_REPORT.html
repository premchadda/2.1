🏗️ 2. Architecture Design

The Card Ordering System uses a 4-layer architecture for flexible content positioning.

⚛️ Frontend (React)
⬇️
🔌 Card Order API
⬇️
🚀 Backend (Express)
⬇️
🐘 PostgreSQL Database
👁️ Layer 1: VISIBILITY CONTROL
is_visible, is_active, visibility_status → Determines IF content should appear
⭐ Layer 2: PROMINENCE CONTROL
is_pinned, is_featured, priority_weight → Determines HOW PROMINENTLY content appears
🔢 Layer 3: SEQUENCE CONTROL
display_order, sort_mode, section_group → Determines POSITION in list
📊 Layer 4: FALLBACK SORTING
created_at, popularity_score, alphabetical → Used when explicit order not set

Master Sorting Rule (SQL)

-- Universal Ordering Query Pattern ORDER BY -- Layer 1: Visibility is_active DESC, is_visible DESC, -- Layer 2: Prominence is_pinned DESC, is_featured DESC, priority_weight DESC, -- Layer 3: Sequence display_order ASC NULLS LAST, -- Layer 4: Fallback created_at DESC

🔍 4. Problems Analysis

🔴 CRITICAL Inconsistent Field Names

Different tables use different field names: order vs sortOrder vs orderIndex causing developer confusion and bugs.

🔴 CRITICAL Hardcoded Arrays

Quick Access items hardcoded in Dashboard.jsx and Home.jsx - requires code change to reorder, same order for all users.

🟠 MEDIUM No Bulk Reorder

Must move items one at a time - time-consuming for admins managing large content libraries.

🟠 MEDIUM No Audit Trail

Order changes not logged - can't track who changed what and when.

🟢 MINOR No User Personalization

Users can't customize their view - limited UX flexibility.
